# Corpus database

Keep one writer database per country. Publish each serving release into a separate, immutable database. Keep a separate serving control database. Serve Vietnam from VNGCloud. Keep account data outside every corpus snapshot. Build all three database kinds on fresh Goose chains that never share a table with the legacy schema.

## Topology decision

**Decision:** Use country writers, immutable country-release databases, and separate control storage.
**Why:** Builds and mutable control state cannot affect a pinned evidence snapshot. Preserve the approved country boundary ([source boundaries](../plans/corpus-redesign-source.md#boundaries)).
**Rejected:** Shared-country writers and in-place publication, for the isolation costs below.
**Detail:** Database names are private handles; country-qualified keys are public identities.

| Option | Isolation, migrations, backups, cost, and adding a country | Decision |
|---|---|---|
| One mutable database per country for writing and serving | Country restore and migration are independent. Few copies, but builds compete with reads and readers can see mixed stages. | The legacy deployment. Frozen, not extended. |
| One database with a country key | One migration chain and shared capacity. Every key, join, authorization rule, and index needs country scoping. Restore and failure affect all countries. | Reject. |
| Shared writer, country-release serving databases | Isolates serving, but write migrations, backups, and mistakes still cross countries. | Reject. |
| One writer per country, separate database per serving release, separate serving control database | Independent country migrations and backups. Snapshot storage multiplies; migration and restore automation repeats per country. Adding a country provisions a writer and release bundle without changing another country's tables. | Recommend. |

Vietnam corpus generation uses one VNGCloud writer database in Vietnam, orchestrated by Temporal Cloud. The country writer alone authors revisions and desired selection. The serving control database holds imported manifests, applied selection, pins, and local retention claims; it cannot author promotions. Serving requests need no writer connection. Databases sharing an instance share CPU, memory, disk failure, and physical recovery, so writer and worker capacity stay separate from the serving host. Use distinct roles and revoke public connection grants. Never route Vietnam requests to an AWS database as a fallback. The serving PostgreSQL listener remains socket-only. The writer may use private TLS only after network, certificate, role, revocation, and fail-closed connectivity controls pass implementation gates.

A serving release contains only the selected evidence closure, policy, identity mappings, artifact handles, and frozen manifest. Exclude job queues, embedding caches, mutable activation records, account state, quarantine actors, and unused historical parser outputs. The closure includes known historical legal text needed for date queries. Serving uses SELECT-only corpus roles; its control role acquires and closes pins without storing question text.

Every application table has `id bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY`, including join tables and projections. Stable UUIDs, digests, singleton checks, and composite business identities use UNIQUE constraints. Keep no foreign keys across schemas. Fenced adapters validate cross-schema references at acceptance; publication repeats closure anti-joins. Same-schema foreign keys reference a single ID and never cascade-delete evidence. Goose owns its version-table shape ([engineering rules](../../instructions/engineering.md#data-and-generated-code)).

## Migration chains and generated stores

**Decision:** Use three chains, one per database kind: writer, release, and control. Each chain owns every schema in its database and has one Goose version table.
**Why:** The three databases have different tables, roles, vector types, and indexes. A writer never holds a frozen manifest copy; a release never holds a job queue; control never holds evidence. One chain per database makes the migrator, the replay test, and the populated-upgrade check one unit per database and lets a slice edit one file set.
**Rejected:** One chain per schema as legacy did (five version tables per database with hand-ordered cross-schema dependencies and nothing to separate); one shared chain for writer and release (the release needs fixed `vector(D)` and HNSW, the writer needs recipe-checked vectors and no serving index, and empty work tables would still receive serving grants); appending to the legacy chains.
**Detail:** Writer schemas are `ingest`, `bronze`, `silver`, `gold`, and `config`. Release schemas are `silver`, `gold`, `config`, and `release`. The control schema is `control`. **Decision:** Put the chains under `deploy/corpusmigrations/{writer,release,control}/` with version tables `public.goose_db_version_corpus_writer`, `public.goose_db_version_corpus_release`, and `public.goose_db_version_corpus_control`.
**Why:** The directory sits beside `deploy/authmigrations/` and outside the frozen `deploy/migrations/` tree, so the frozen-chain check stays a plain path rule. **Rejected:** New directories under `deploy/migrations/`; version tables inside a chain-owned schema; timestamp file names (the chains are edited in place by one persistence lane, so five-digit sequence numbers read in dependency order).
**Detail:** `deploy/corpusmigrations/embed.go` exports `FS embed.FS` with globs `writer/*.sql`, `release/*.sql`, `control/*.sql`, and the `inventory/*.json` object inventories described below. **Decision:** Privileged provisioning installs `vector` and `btree_gist` in `public` before the migrator runs; the non-superuser migration login never runs `CREATE EXTENSION`.

**Rejected:** A superuser migration login; `CREATE EXTENSION IF NOT EXISTS` inside `00001`; a patched trusted pgvector build.
**Detail:** Provisioning runs as the instance superuser in CI and as the VNGCloud database administrator: it creates the database, installs both extensions in `public`, and runs the bootstrap file before the migrator connects. Writer and release `00001` read `pg_extension` and fail unless both extensions exist in `public` at the approved versions. The reset baseline pins `vector` 0.8.2 and `btree_gist` 1.7, the version PostgreSQL 17 ships ([btree_gist control](https://raw.githubusercontent.com/postgres/postgres/REL_17_STABLE/contrib/btree_gist/btree_gist.control)); hosted verification on VNGCloud may move a pin in one reviewed change. **Detail:** `cmd/corpus-migrate/main.go` reads only `BANHMI_CORPUS_MIGRATION_DATABASE_URL`. Before any Goose call, take `pg_advisory_lock(1129271888, 1)` on one pinned connection and hold it until every Goose call and the final version check end; then release it with `pg_advisory_unlock` on that connection. The key is the same for all three chain choices so they serialize, advisory locks are database-scoped, and Goose may run on a separate connection. With an applied version, require exactly the selected chain's schema set and a contiguous known version history, then compare the catalog with the chain's object inventory at that version: every relation of any `pg_class` kind, function, trigger, and type inside each selected schema must be declared for that version, except the row and array types PostgreSQL creates for declared relations, and every declared object must exist. The migration login must own the version table, every selected schema, and every inventoried relation, function, and type; a trigger has no owner, so its parent relation's owner counts for it. Reject undeclared, missing, or legacy objects, any of those objects owned by another role, and objects in `public` other than approved extension objects and that version table's dependencies. Every rejection precedes the first Goose call and creates nothing. Catalog or permission errors fail closed. Deployment supplies an exclusive, database-scoped migration principal.

The inventory is `deploy/corpusmigrations/inventory/{writer,release,control}.json`, embedded through a fourth `embed.go` glob `inventory/*.json`. Each entry names schema, kind, identity, the version that creates the object, and, for a dropped or renamed object, the version that removes it; the expected set at version V is the entries created at or before V and not removed by V. Identity is portable and never an OID: a relation or type uses its name; a function uses its name plus `pg_get_function_identity_arguments`, so an undeclared overload is an undeclared object; a user trigger uses its owning table plus its name, because `pg_trigger.tgname` is unique only per table. Internal triggers (`pg_trigger.tgisinternal`) are never inventoried, because PostgreSQL generates their names and embeds OIDs in foreign-key trigger names; the guard accepts an internal trigger only when its `tgconstraint` points to a constraint on an inventoried relation in a selected schema and rejects every other internal trigger. Every migration edit changes the inventory in the same slice, and the replay tests compare the catalog with the inventory after every prefix. This is an object inventory, not a schema differ or checksum system; columns, constraints, and index definitions stay in the migration files.

`-status` uses direct catalog and version-table SELECTs inside a read-only transaction, reporting all files pending when the version table is absent. Do not call Goose `StatusContext` or `EnsureDBVersionContext`: the [pinned implementation](https://github.com/pressly/goose/blob/v3.27.0/status.go) can create the version table. **Decision:** Restore a release dump as the restore login with `pg_restore --no-owner --no-acl --no-comments --exit-on-error --role=<release migration login>` from a reviewed `--use-list` TOC that excludes `EXTENSION` entries.
**Why:** The loader holds only SELECT, INSERT, and sequence USAGE and cannot create schemas, tables, functions, constraints, or indexes. `--role` makes the migration login create and own every restored object, so no ownership transfer follows. `--no-acl` drops the dumped grants, and the restored Goose history prevents rerunning `00001` to recover them ([pg_restore](https://www.postgresql.org/docs/17/app-pgrestore.html)).
**Rejected:** Restoring as the loader or a superuser; `REASSIGN OWNED` after a restore owned by the restore login; rerunning migrations to recover grants; a grant script outside the bootstrap directory; the migration login revoking the restore membership, which it cannot do because it holds no `ADMIN OPTION` on its own role.
**Detail:** Provisioning installs the extensions, creates the database, and runs bootstrap `release.sql` with `restore_login_role`, which grants the restore login `CONNECT` and the temporary membership. After `pg_restore` exits, two principals finish the procedure. First, the migration login runs `deploy/corpusmigrations/bootstrap/release-grants.sql`, which repeats the reader grants of release `00001` and `00002`; the loader has no grant in a restored database. Second, the provisioning administrator, the grantor of both, runs `deploy/corpusmigrations/bootstrap/release-restore-close.sql`, which revokes the restore login's membership in the migration login and its `CONNECT` on the database ([REVOKE](https://www.postgresql.org/docs/17/sql-revoke.html)). Readiness requires all three: `corpus-migrate -chain release -status` reports no pending files, the role check above shows no restore membership, and `has_database_privilege` denies the restore login `CONNECT`. `TestReleaseRestoreGrants` in `internal/corpus/store/projection/schema_integration_test.go` dumps a sealed candidate, restores it this way, runs the grant file as the migration login and the close file as the test's provisioning administrator, asserts that migration-login revocation attempts leave the restore membership and effective `CONNECT` unchanged, accepting a permission error or warning without effect, that the provisioning administrator's close file removes both, and that the reader's effective privileges equal those after a fresh chain replay, that the reader reads every allowlisted table, that reader INSERT, UPDATE, DELETE, and TRUNCATE fail, and that the restore and loader logins hold no membership, grant, or `CONNECT`.

**Decision:** Generate stores with sqlc entries that read a chain directory as schema input, with query directories and generated output beside the code that uses them under `internal/`.
**Why:** The engineering rule puts new queries and stores under `internal/`. Several entries can read one chain so each store package holds only its consumer's queries and models.
**Rejected:** New packages under `pkg/store/` or `sql/`; one generated package per chain (M1 would import release and vector models it cannot use); generated code in a shared `gen` package.
**Detail:** Each `sqlc.yaml` entry uses its name below, `engine: postgresql`, `sql_package: pgx/v5`, `emit_interface: true`, and `omit_unused_structs: true`. Map `jsonb` to `encoding/json.RawMessage`, `timestamptz` to `time.Time`, nullable text/int4/int8 to `*string`/`*int32`/`*int64`, `vector` to `github.com/pgvector/pgvector-go.Vector`, and `sparsevec` to `string`. Nullable timestamps/vectors/sparse vectors use pointers; nullable JSONB keeps RawMessage. Do not map dense vectors to strings. Each entry's `out` directory is a child package of its store, named `<store>db`, and holds only generated Go; handwritten adapters, transactions, and tests live in the store package and import the child. The hosted generation job empties every `out` directory before `sqlc generate`, regenerates every entry, and fails on drift, so a handwritten file inside an `out` directory is deleted. Add an entry with its first query, in the order below.

## Identity, revisions, and release membership

Mint universally unique identifiers (UUIDs) once in `silver.document_identity`. Use `vn:doc:<uuid>`. Keep country and entity kind, but exclude domain, brand, title, source number, and local sequence. Retain identity assertions and the catalog through every writer rebuild and backup restore. Reject keys whose country differs from the writer's singleton country metadata in `ingest.country_admission`.

Use `vn:doc:<uuid>:rev:<digest>` for an immutable document revision. Compute the digest from canonical source-observation hashes, text and metadata hashes, and conversion, normalization, parser, and policy recipes. Exclude local IDs and processing timestamps. Identical inputs reuse revisions; metadata changes create distinct revisions. `silver.document_revision` has UNIQUE `(document_identity_id, revision_key)` with metadata identity inside the key, `intake_execution_id NOT NULL` as origin provenance, and no build column. Immutable-row triggers reject UPDATE and DELETE.

`ingest.build_revision` records membership with UNIQUE `(build_id, document_revision_id)` so builds reuse immutable revisions. Publication validates selected acceptance receipts and membership, not origin-build equality. Export stable keys; local IDs may change.

A provision key contains the document revision digest and a revision-local provision key. Preserve native citation bytes and source anchors separately. A stable provision UUID is optional and needs an approved continuity assertion. Never infer continuity from matching text or renumbering. Chunk IDs remain local to a chunk set. Citations carry evidence key, revision key, release ID, native citation, and source hash. The write path computes amendment differences; the database stores them. The [website design](../design/website.md#phase-3-depends-on-the-corpus-redesign) owns redline display.

Legacy evidence enters only through an import contract, never through a shared table. `silver.legacy_identity_mapping` uses UNIQUE `(export_manifest_digest, entity_kind, legacy_id)` within the country database. The manifest supplies and validates country. Store state `resolved`, `ambiguous`, or `unavailable`; only `resolved` has a non-null `document_identity_id`. Retain ambiguous candidates in its immutable hashed report, not an arbitrary selected ID. Its input is a hash-pinned identity export manifest listing legacy document ID, source, external ID, normalized document number, and title hash, produced by a read-only hosted export from the legacy `banhmi` database subject to owner question 4. The import runs as an intake execution whose receipt records the manifest digest. Only document identities are mapped; legacy section and chunk IDs are not. A bare legacy ID resolves only when all retained mappings agree. The frozen Vietnam goldens in `deploy/eval/golden.json` cite document numbers and articles, so evaluation resolves them through identity and native citations and needs no ID mapping. Merges and splits append identity assertions and keep old keys resolvable.

Methods initially mean official classification, deterministic rule, or human review. Confidence describes that method's support, not legal truth. Record inheritance and unresolved scope explicitly.

Maintain assessment rows even when no positive assignment exists. States are `assigned`, `unknown`, `unreviewed`, and `reviewed_not_applicable`. An absent row means unknown. Report unknown and unreviewed counts, taxonomy version, and denominators through `corpus_status` and `quality_gaps`. Never report missing tags as zero coverage.

The default subject search retrieves two labelled sets: approved primary matches and possible matches whose classification is unknown or unreviewed. Apply the same eligibility predicate to both dense and lexical arms before their candidate LIMIT. Fuse within each set using the embedding design's contract. Return possible matches separately with a coverage gap. An explicit strict subject filter excludes possible matches and reports that recall is limited by classification coverage. Multiple selected subjects use union semantics, including descendants.

Fetch amendment, repeal, and validity context after primary selection regardless of its subject. Label context roles. Reject vector copies and partitions per subject because laws have multiple tags. Subject filtering must not add hidden recall loss through fixed unfiltered top-k or missing labels. Measure approximate retrieval against exact eligible-set retrieval.

## Parts, validity, and relations

Bronze observations, artifacts, manifests, and Silver evidence rows reject UPDATE and DELETE; every chain also revokes TRUNCATE from non-migration roles. Acceptance states are separate. Corrections append a new assessment or revision; they never rewrite an old review state. The write path owns execution and legal-effect resolution. A partial-document badge cannot override a resolved provision interval. The other five clauses must not appear as amendments to that target without their own target evidence.

Reject a JSON-only target field and document-only validity inheritance. Keep verbatim replacement text and before-and-after revision links; do not generate consolidated text at query time.

## Vector and lexical storage

Recommend cosine hierarchical navigable small world (HNSW) indexes for scaling, initially `m=16`, `ef_construction=64`. Preserve Vietnam's exact scan until HNSW passes every accepted golden case. Build HNSW only in release databases after bulk load, never over all historical writer vectors. Gold evidence is append-only: new chunk, vector, lexical, or subject outputs use a new recipe or set identity; mutable progress stays in the ledger.

| **Decision** | **Why** | **Rejected** | **Detail** |
|---|---|---|---|
| HNSW after load | Bounds serving search cost if qualified | IVFFlat needs training/tuning; defer it | Keep exact scans until measured recall and latency pass |
| Float32 baseline | Preserve parity | Unmeasured half precision or binary quantization | Storage starts with f32; changing precision needs its own gate |
| 1,024 baseline dimensions | Match the retained recipe | Silent truncation | Also define the 768 candidate table; selecting it requires embedding approval |
| Country/release databases; subject child rows | Preserve isolation and shared laws | Shared historical graphs and subject partitions | Revisit writer partitioning only after measured growth |
| Exact sparse ranking | Preserve lexical recall | Sparse ANN or a new search engine without evidence | Rank eligible rows with sparse inner product |

Support the embedding sibling's 768-dimensional candidate beside the 1,024-dimensional baseline. `gold.chunk_vector` in the writer stores `vector` with a recipe identity and a dimension check; each release table is fixed `vector(D)` or approved `halfvec(D)`, one table per approved pair. Replace hardcoded dimensions and release validators together, including [types.go:28](../../internal/corpus/release/types.go#L28). Half precision remains a separate experiment.

The [pgvector documentation](https://github.com/pgvector/pgvector#hnsw) describes HNSW's higher memory and build cost relative to IVFFlat and recommends creating indexes after loading data. HNSW supports `vector` to 2,000 dimensions and `halfvec` to 4,000; sparse HNSW permits 1,000 nonzero elements. Approve a compatible dimension and precision before changing the chain. Never mix serving recipes.

Require pgvector 0.8 or later and pin an exact tested extension version. Iterative scans continue filtered approximate scans until enough rows or a scan limit; they do not guarantee exact recall ([iterative scans](https://github.com/pgvector/pgvector#iterative-index-scans)). Use transaction-local `hnsw.iterative_scan=strict_order`, bounded scan and memory settings, and a tested custom-plan policy. Put subject and date eligibility inside the ordered scan using indexed EXISTS predicates. Verify the actual plan: outer filtering after a fixed candidate LIMIT defeats iterative replenishment. Use an exact distance scan for small eligible sets or candidate shortfall. An exact fallback that cannot finish within the deadline returns a retryable error, not a silently incomplete success.

`gold.chunk_lexical_vector.content_sparse` is `sparsevec(1048576)` bound to a `gold.lexical_revision`. Preserve the 2^20 hash space and deterministic tokenizer contract. Recompute BM25 weights for the entire selected chunk set; never combine old and new corpus statistics. Query vectors represent term presence in the existing implementation ([bm25.go:1](../../pkg/rag/lexical/bm25.go#L1)). `gold.lexical_statistics` persists corpus statistics and recipe digest for audit and rebuild, so serving never loads all source text at startup. Use chunk-identity B-trees and exact `<#>` ranking. No lexical approximate nearest neighbor (ANN) graph is budgeted. If scans miss budget, benchmark term postings before exact scoring and require parity.

The following are calculated payload sizes and planning estimates per million chunks. GiB means 2^30 bytes. Payload formulas are `4D+8` for vector, `2D+8` for halfvec, `D/8+8` for bit, and `8Z+16` for sparsevec, where D is dimensions and Z is nonzero entries ([type reference](https://github.com/pgvector/pgvector#reference)). Heap, page, and index overhead are extra.

| Component per million chunks | Payload GiB | Planning allowance GiB |
|---|---:|---:|
| Float32, D=1,024 | 3.82 | Dense heap 4.5-6; HNSW separately 5-8 |
| Half precision, D=1,024, alternative | 1.91 | Heap 2.5-3.5; HNSW separately 3-5 |
| Binary, D=1,024, alternative | 0.13 | Graph and retained original vectors are additional; not selected |
| Sparse, Z=200 assumption | 1.51 | Heap 2-3; no ANN graph |
| Text, provenance, validity, subjects, B-trees | Unknown | 12-23, including selected historical evidence |
| Selected serving snapshot total | Not measured | 24-40 |

Measure database working set on the selected release; do not extrapolate a launch RAM reservation from a million-chunk estimate. Budget one query embedder separately. Bound `work_mem` and index-build concurrency together.

## Risks and owner questions

Snapshots and BM25 revisions can dominate storage. Historical coverage and subject fan-out are unknown. HNSW row counts do not prove recall. Exact lexical scans may breach latency targets. Lost identity catalogs cannot be reconstructed safely from titles. Schema cannot repair attribution. Control failure can block pins despite healthy snapshots; include control in recovery planning. Writer and release evidence tables are defined twice; the `projection` store's load tests must prove every release column has a writer source or the derivation rule above.

1. Approve one year of archives beyond the online retention minimum? Recommend one year, including recipe artifacts needed for restore. Online retention remains active plus at least two prior releases for at least 30 days, plus explicit pins or holds. Price longer dossier guarantees separately.
2. Should subject filters include unclassified evidence? Recommend a separate possible-match set by default. Strict filtering must warn about coverage.
3. Which corpus recovery targets should hosting prove? Recommend no lost activated manifests, identity keys, or acknowledged holds, four-hour restore, and at most 24 hours of unpublished work lost. Auth recovery remains [hosting owner question 1](vngcloud-hosting.md#risks-and-owner-questions).
4. Approve a one-time read-only hosted export of Vietnam document identities from the legacy `banhmi` database for `silver.legacy_identity_mapping`? Recommend yes, as a protected workflow with a hash-pinned manifest and no write access, before M4 serving rehearsal. Without it the `document` tool resolves no legacy IDs and reports that gap.

Unverified: per-release storage sizes, live extension versions, traffic, restore speed, hardware latency, VNGCloud limits and backup cost, historical coverage, owner-supplied legal examples, and whether the VNGCloud database administrator can install `vector` 0.8.2 and `btree_gist` 1.7. No runtime or deployed checks ran.
